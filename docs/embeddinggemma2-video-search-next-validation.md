# 联合表示失败后的有限对照提案

状态：用户于 2026-10-15 同意的有限纯音频对照、随后批准的固定规则离线融合均已完成。原实施边界与冻结验收成绩不变，见[验收记录](embeddinggemma2-video-search-acceptance.md)。

首轮有限候选中，画面 5/5、对白 3/5，两条预期无答案都有错误候选；对白未达到 4/5 门槛。目标确已入库，失败两条最高均排第六。相邻窗口抑制的离线诊断仍不能使其进入前三。当前没有接口、音轨或切窗错误的具体反证，也不能宣布模型本身失效。

建议只验证一个问题：保持这些窗口不变，将输入换成声音之后，对白目标能否排得更靠前。

- 使用同一 14 个派生样本、42 个已记录的实际窗口和默认音轨，不改变时间网格、查询、目标或原始排名。派生时间窗不等同于完整原片从零开始的网格。
- 只调用现有 embedding-service 的独立 `audio` 输入，最多新增 42 个音频表示。已保存且与文字、模型签名对应一致的查询向量可复用；其余最多重新嵌入五条对白及两条负例的七条文字。
- 本机私有验证区分别保存表示种类、窗口、模型／revision／processing_id、维度及实际音频时长。核对真实音轨和完整性；失败项单列，不用零向量填补。
- 原联合索引保留并保持手动暂停。新向量不混入它，不改变产品搜索、模型服务、阈值、窗口或正式实例，不增加转写能力，不分析完整库。
- 比较全部五条对白及两个负例的目标名次、前三实际内容、负例分数分布，以及原已通过对白是否退化。先按相同候选分别排序，不把不同表示的分数直接混成一榜。
- 无论结果如何，保留首轮失败记录。一次对照有改善，只支持继续研究音频检索，不代表双通道产品或整库搜索验收通过；再据结果决定后续路线。

额外处理耗时须实测，不假定增加表示就使耗时恰好翻倍。

## 执行结果

42 个音频表示全部成功，仍是原 14 个候选的 `0–6、4–10、6–12` 窗口。沿用插件的音轨编号、寻址及编码参数重新生成窗口，调用独立 `audio` 字段；响应 `modalities` 仅为 `audio`，单声道 16 kHz，解码时长约 6.000–6.016 秒。原联合索引未写入新表示。

复算七条相同文字查询，重现原联合排名分数，最大差异约 `5.1e-8`。本机 Python 3.9 不支持 `zip(strict=...)`，首次 D1 完整响应在保存前触发脚本错误；修复后仅重新请求同一句 D1。因此共有七条不同文字、八次文字请求，42 次音频请求，没有新增查询或额外音频表示。

## 固定规则离线融合（已批准并执行）

仅复用已经保存的联合与纯音频排名，对同一七条查询、42 个窗口做一次诊断，不调用模型、不重新切窗、不写正式索引、不改变网页。两路前三的并集能覆盖四条已确认对白，但并集最多六条，不能冒充合并后三条的通过率。

事前固定等权倒数排名融合：每个窗口的分数为 `1/(60 + jointRank) + 1/(60 + audioRank)`；名次从 1 开始，两路完整排名都包含同一 42 个窗口。按融合分数降序，完全同分按稳定片段 ID 排序。只测试这一个规则，不试多组权重挑成绩，不逐查询选通道，不同时改变窗口、查询、内容标签或去重规则。算法及常数的背景参考 [Microsoft 的 RRF 说明](https://learn.microsoft.com/en-us/azure/search/hybrid-search-ranking)，该来源不证明本样本必然改善。

分别报告五条对白的原始排名、融合排名及前三实际内容依据；D5 邻近窗口完整声音句意仍作为未知。两条负例同样保留，不能用融合分数套原余弦门槛 0.35，也不从这七条测试查询选新门槛。融合如果改善，只能支持有限候选上的后续探索，无答案拒绝、独立校准与全库验收仍未解决。
